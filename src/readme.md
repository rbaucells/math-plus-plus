# Code Style
- Classes/Structs are PascalCase.
- Namespaces are PascalCase.
- Concepts are snake_case.
- Usings/typedefs are PascalCase.
- Compile-time const variables are ALL_CAPS.
- Template params are ALL_CAPS.
- Macros are ALL_CAPS.
- Local variables are camelCase.
- Global variables are camelCase.
- Member functions are camelCase.
- Free functions are snake_case.
- Loop variables should be one letter (e.g. 'i', 'j', 'k', 'c', 'r', etc.).
- Private member variables are suffixed by '_'.
- File names are short and snake_case.
- Enums are PascalCase and enumerators are snake_case.

# Code Patterns
- Follow mathematical definitions closely, then provide workarounds/shortcuts commonly used in implementation (e.g. Allowing cholesky to work on PSD matrices) through parameters.
- Be explicit:
  - If in a templated class, don't shorten MyClass\<T> to MyClass.
  - Never use 'auto' unless absolutely needed (e.g. std::apply on a tuple).
  - Delete unused constructors even if implicitly deleted.
- Descriptive function comments for everything. Must include:
  - A one-liner '@brief' section.
  - A '@param' section for every argument.
  - If function returns, '@returns' section.
  - A '@tparam' section for template parameters.
  - If the function may throw, '@throws' section.
- Function comments must also provide:
  - How much memory is allocated in bytes.
  - For more complex algorithms do:
    - Provide a link to a paper or article for more info.
    - Show how and when to use for common use cases like solving Ax = b.
    - Say the time complexity in Big O notation.
- For data types that are primarily public, use structs, else use classes
- 1 action per line, basically don't increment a pointer, dereference it, and call a method in one line.
- Avoid overusing 'using' and 'typedef' statements.
